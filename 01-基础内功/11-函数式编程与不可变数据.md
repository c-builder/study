# 函数式编程与不可变数据

## 学习目标

- 理解纯函数、副作用、不可变性等核心概念
- 掌握高阶函数、柯里化、函数组合的原理与应用
- 理解不可变数据为何是 React/Redux 的基石
- 能用函数式思想写出可测试、可预测的代码

## 为什么需要

现代前端深受函数式编程（FP）影响：React 组件是「输入 props 输出 UI」的函数，Hooks 强调纯函数与不可变更新，Redux 的 reducer 必须是纯函数，RxJS、Lodash/fp、Ramda 都是 FP 实践。理解 FP 不是为了炫技，而是写出**可预测、易测试、易并发**的代码。

> 核心心法：**相同输入永远得到相同输出，且不修改外部状态。** 这让代码可推理、可缓存、可测试。

## 一、纯函数与副作用

### 纯函数

满足两个条件：

1. **相同输入 → 相同输出**（不依赖外部可变状态）
2. **无副作用**（不修改外部、不发请求、不操作 DOM、不打印）

```javascript
// 纯函数：可预测、可缓存、可测试
const add = (a, b) => a + b;

// 非纯：依赖外部 + 修改外部
let total = 0;
const addImpure = (n) => { total += n; return total; };

// 非纯：副作用（请求/DOM/随机/时间）
const now = () => Date.now();
```

### 副作用隔离

副作用不可避免（请求、DOM、日志），FP 的策略是**把副作用推到边界**，核心逻辑保持纯净：

```javascript
// 纯：计算逻辑
const calcTotal = (items) => items.reduce((s, i) => s + i.price, 0);

// 不纯：仅在边界做 IO
async function checkout(items) {
  const total = calcTotal(items);     // 纯
  await api.pay(total);               // 副作用在边界
}
```

> React 把这一思想制度化：渲染函数要纯，副作用进 `useEffect`。

## 二、不可变性（Immutability）

不修改原数据，而是返回新副本。这是 React/Redux 状态管理的基石。

### 为什么需要

```javascript
// React 靠引用比较判断是否更新（Object.is）
// 直接 mutate → 引用没变 → 组件不重渲染（bug）
state.list.push(item);        // ✗ 引用未变
setState(state);              // 不触发更新

setState({ ...state, list: [...state.list, item] }); // ✓ 新引用
```

### 不可变更新模式

```javascript
// 数组
const added   = [...arr, item];
const removed = arr.filter(x => x.id !== id);
const updated = arr.map(x => x.id === id ? { ...x, done: true } : x);

// 对象（含嵌套）
const next = {
  ...state,
  user: { ...state.user, name: 'New' },   // 每层都要展开
};
```

> 嵌套深时手动展开繁琐易错 → 用 **Immer** 用「可变写法」产出不可变结果：

```javascript
import { produce } from 'immer';
const next = produce(state, draft => {
  draft.user.profile.name = 'New';   // 看似 mutate，实际生成新对象
});
```

### 浅拷贝 vs 深拷贝

```javascript
const shallow = { ...obj };        // 浅：嵌套仍共享引用
const deep = structuredClone(obj); // 深：完全独立（含 Date/Map/Set）
```

## 三、高阶函数（HOF）

接收函数或返回函数的函数，是 FP 的基本构件：

```javascript
// 数组三剑客本身就是 HOF
[1,2,3].map(x => x * 2);
[1,2,3].filter(x => x > 1);
[1,2,3].reduce((s, x) => s + x, 0);

// 返回函数：封装可复用逻辑
const withLog = (fn) => (...args) => {
  console.log('call', args);
  return fn(...args);
};
const loggedAdd = withLog(add);
```

React 的 HOC（高阶组件）、自定义 Hook 都是这一思想的体现。

## 四、柯里化与偏应用

把多参函数转为一系列单参函数，便于复用与组合：

```javascript
// 柯里化
const curry = (fn) => {
  return function curried(...args) {
    return args.length >= fn.length
      ? fn(...args)
      : (...rest) => curried(...args, ...rest);
  };
};

const add3 = curry((a, b, c) => a + b + c);
add3(1)(2)(3);     // 6
add3(1, 2)(3);     // 6

// 应用：预设参数，生成专用函数
const request = curry((method, url, body) => fetch(url, { method, body }));
const post = request('POST');           // 复用
post('/api/users', data);
```

## 五、函数组合（Compose / Pipe）

把多个小函数串成数据处理管道——FP 的精髓：

```javascript
const pipe = (...fns) => (x) => fns.reduce((acc, fn) => fn(acc), x);
const compose = (...fns) => (x) => fns.reduceRight((acc, fn) => fn(acc), x);

const trim = s => s.trim();
const toLower = s => s.toLowerCase();
const slug = s => s.replace(/\s+/g, '-');

const toSlug = pipe(trim, toLower, slug);
toSlug('  Hello World  ');   // 'hello-world'
```

```mermaid
flowchart LR
    Input[输入] --> trim --> toLower --> slug --> Output[输出]
```

> 组合让逻辑像「乐高」拼装：每个函数职责单一、可测试，组合成复杂流程。Redux 中间件、RxJS 操作符都是这种管道思想。

## 六、声明式 vs 命令式

```javascript
// 命令式：描述「怎么做」
const result = [];
for (let i = 0; i < nums.length; i++) {
  if (nums[i] % 2 === 0) result.push(nums[i] * 2);
}

// 声明式：描述「要什么」（FP 风格，更易读）
const result = nums.filter(n => n % 2 === 0).map(n => n * 2);
```

React/Vue 的核心也是声明式：你描述 UI 应该是什么样，框架负责 DOM 操作。

## 排查实战

### 案例 A：React 列表更新不渲染

- **原因：** 直接 `arr.push` 后 setState，引用未变
- **修复：** 用 `[...arr, item]` 等不可变更新
- **验证：** 组件正确重渲染

### 案例 B：嵌套状态更新「漏层」

- **现象：** 改深层属性后部分组件不更新
- **原因：** 只改了内层但外层引用没变
- **修复：** 每层展开，或用 Immer
- **验证：** memo 子组件按预期更新

### 案例 C：纯函数里混入副作用难以测试

- **原因：** 计算函数里 `Date.now()`/请求
- **修复：** 把时间/IO 作为参数传入，逻辑保持纯
- **验证：** 单测可固定输入断言输出

## 常见误区与最佳实践

| 误区 | 正确理解 |
|------|---------|
| "FP 就是用 map/filter" | 核心是纯函数 + 不可变 + 组合 |
| "不可变=性能差" | 结构共享 + memo 反而利于优化 |
| "展开就安全了" | 浅拷贝，嵌套仍要逐层处理 |
| "纯函数没副作用没用" | 副作用推到边界，核心保持纯 |
| "柯里化是炫技" | 用于复用与组合，按需使用 |

**可执行清单：**

- [ ] 状态更新一律不可变（数组/对象展开或 Immer）
- [ ] 计算逻辑写成纯函数，副作用进 effect/边界
- [ ] 优先声明式（map/filter/reduce）替代手写循环
- [ ] 复杂数据流用 pipe/compose 拆成小函数
- [ ] 纯函数配合 memo/useMemo 做缓存优化

## 面试高频问答（追问链）

> 大厂对一个考点通常追问到能力边界：**概念 → 机制 → 边界 → ⭐ 原理（触底）→ 实战（落地）**。实战层是区分「背过」和「做过」的关键。

### 链一：纯函数与副作用

1. **概念**：纯函数？→ 相同输入相同输出、无副作用。
2. **机制**：为什么纯函数易测试/可缓存？→ 无外部依赖，可记忆化、可并行。
3. **应用**：副作用怎么管理？→ 推到边界（函数式核心 + 命令式外壳）。
4. ⭐ **原理（触底）**：React 为什么要求 reducer/render 是纯函数？→ 并发渲染会重复调用、丢弃中间结果；不纯会导致状态撕裂与不可预测。
5. **实战（落地）**：Reducer 里误改 state 怎么发现和修？→ ESLint 禁 mutate；Immer 包 reducer；单测断言引用变化；React StrictMode 双调用暴露副作用，修后 Profiler 无异常重渲染。

### 链二：组合与不可变

1. **概念**：柯里化 vs 偏应用？→ 柯里化单参链式、偏应用预设部分参数。
2. **机制**：compose vs pipe？→ 右到左 vs 左到右。
3. **边界**：不可变更新 vs 深拷贝？→ 结构共享只拷贝变更路径，未变部分复用引用。
4. ⭐ **原理（触底）**：Immer 怎么用 Proxy 实现「写起来可变、结果不可变」？→ 拦截草稿对象写操作，仅对修改路径 copy-on-write 生成新对象，其余共享引用，兼顾性能与不可变。
5. **实战（落地）**：复杂嵌套 state 更新怎么写？→ Zustand/Redux 配 Immer，`produce(draft => { draft.list[i].name = x })`；对比手写展开少 70% 代码；单测验证未改字段引用不变。

## 小结

- 纯函数 = 相同输入相同输出 + 无副作用，是可测试可推理的基础
- 不可变更新是 React/Redux 的基石，靠引用变化驱动渲染
- 高阶函数、柯里化、组合让逻辑可复用、可拼装
- 副作用推到边界，核心逻辑保持纯净
- 声明式代码更贴近「要什么」，更易维护
